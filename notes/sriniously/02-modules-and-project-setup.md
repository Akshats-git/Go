## The first program

```go
package main

import "fmt"

func main() {
	fmt.Println("hello 世界")
}
```

Run it:

```bash
go run main.go
```

Four things are happening: a **package declaration**, an **import**, a **function named `main`**, and a call into the imported package.

## `go.mod`

[▶ 27:51](https://www.youtube.com/watch?v=tgGNwG_UxFo&t=1671s)

```
module github.com/username/projectname

go 1.22
```

Generated by:

```bash
go mod init github.com/username/projectname
```

### What a `go.mod` file holds — three things

1. **Module name** — the name of the project. By convention prefixed with your code-hosting provider (`github.com/`, `gitlab.com/`, `bitbucket.org/`) plus username/org.
2. **Go version** — the *minimum* Go version this project depends on. Not necessarily the version installed on your machine.
3. **External dependencies** — every package the project uses, pinned to exact versions.

### Why the hosting-provider prefix

Because a Go project is one of two kinds:

| Kind | What it is | What you do with it |
|---|---|---|
| **Executable** | A program you run | You **run** it |
| **Library / package** | Code others import | You **import** it |

Backend projects are executables. But the module path doubles as the import path if anyone ever imports you, so the unique, URL-shaped name is the convention either way.

### Dependency workflow

```bash
go get github.com/aws/aws-sdk-go   # adds the package + version to go.mod
go mod download                     # a teammate fetches every pinned dep in one command
```

That's the payoff: a teammate clones the repo, runs one command, and gets the exact same dependency set — no manual `go get` per package.

**You will almost never hand-edit `go.mod`.** Commands maintain it. The exception is pinning a specific version manually.

### Real-world look

fider's `go.mod`: module name `github.com/getfider/fider`, a Go version line, then a long `require` block of external packages with exact versions. Same three parts, just bigger.

## `main.go` anatomy

[▶ 37:13](https://www.youtube.com/watch?v=tgGNwG_UxFo&t=2233s)

### The `main` package rule

Every `.go` file starts with a package declaration. For an **executable**:

- There must be a package named `main`
- Inside it there must be a `func main()`
- That function is the **entry point** — where execution begins

### Imports

```go
import "fmt"
```

No prefix ⇒ it comes from the **standard library**. Standard library packages don't need installing (they ship with the Go runtime), but they still need importing.

A prefix like `github.com/...` ⇒ external package, or a package from your own module.

`fmt` = formatting/printing/string manipulation.

### The capital letter

```go
fmt.Println(...)   // capital P — not optional
```

Anything accessed from *another* package must start with a capital letter. That's Go's encapsulation mechanism. Covered in [03 — Packages & visibility](03-packages-and-visibility.md).

## UTF-8 support

[▶ 44:43](https://www.youtube.com/watch?v=tgGNwG_UxFo&t=2683s)

The `世界` in the hello-world string isn't decoration — it demonstrates that Go source and strings are **UTF-8** natively.

- Older languages leaned on **ASCII**: 128 code points (0–127) — lowercase a–z, uppercase A–Z, 0–9, and some punctuation. Deeply limiting for a world with thousands of writing systems.
- Go's designers built on **Unicode**, encoded as **UTF-8**, covering characters from essentially every written language.

> ⚠️ **Correction:** the video says UTF-8 covers "around 12,000 characters." Unicode actually defines ~150,000 characters across ~160 scripts. The point stands — vastly more than ASCII.

Related types (see [05 — Variables & types](05-variables-and-types.md)):
- `byte` = alias for `uint8` — raw bytes of a string
- `rune` = alias for `int32` — one Unicode code point

## `go build` vs `go run`

[▶ 47:00](https://www.youtube.com/watch?v=tgGNwG_UxFo&t=2820s)

```bash
go build main.go   # produces an executable file named "main"
./main             # run it
```

```bash
go run main.go     # compile and execute in one step, no binary left behind
```

### Cross-compilation — Go's headline feature

```bash
GOOS=windows GOARCH=amd64 go build .   # produces a .exe, from macOS or Linux
GOOS=linux   GOARCH=amd64 go build .
```

- One command produces a **single self-contained binary** for a different OS/architecture.
- The Go runtime and all dependencies are **embedded into the binary**. Ship it to a machine with no Go installed and it just runs.
- If you omit `GOOS`/`GOARCH`, it builds for your own platform.

This is why Go is so pleasant to deploy: no runtime to install, no dependency tree to resolve on the target machine.

### Which to use when

| Command | Use it | What it does |
|---|---|---|
| `go run` | **Local development** | Compiles, executes from a temp location, leaves no artifact |
| `go build` | **Deployment, CI/CD, distribution** | Compiles and writes a binary you can ship |

> ⚠️ **Correction:** the video says `go build` throws away compilation results and `go run` caches them, making `go run` faster. That's backwards/garbled. In reality **both use the same shared build cache** (`go env GOCACHE`), so both benefit from incremental rebuilds. The real difference is only where the binary lands: `go build` writes it into your directory; `go run` builds to a temp dir, executes it, and discards it. The practical advice — `go run` while developing, `go build` when shipping — is right.
